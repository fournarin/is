## 0. สรุปหนึ่งหน้า

### 0.1 ปัญหาของหน้าจอเดิม จากผู้มีส่วนได้ส่วนเสีย

ข้อด้านล่างตรวจซ้ำแล้วหลังการประชุม และตัดข้อที่เกิดจากวิธีถ่ายภาพหรือ demo seed ออกแล้ว (ดู 0.2 ซึ่งในตาราง requirement อ้างเป็น "ข้อเท็จจริงข้อ 1-4")

1. **ไม่มี design system:** ใช้ emoji แทนไอคอนในทุกหน้า หน้าตาเหมือน template ของ SaaS ทั้งแถบฟ้า การ์ดมุมมน และ pill สีพาสเทล ผู้ให้ข้อมูลทุกคนปฏิเสธข้อนี้ทันที
2. **หน้าจอ desktop คือหน้ามือถือที่ยืดออก:** ที่ 1280 px เนื้อหาเป็นคอลัมน์กว้างราว 540 px และมีแถบแท็บล่างแบบมือถือ บนกระดานหัวหน้ากะเห็นงานแค่ 1.5 ใบ เพราะเป็น kanban 4 คอลัมน์ที่ 3 คอลัมน์แทบว่าง
3. **ข้อมูลสำคัญจมอยู่ในประโยค:** จำนวนคันที่จะเสียฝังอยู่ในประโยคตัวเทา ไม่มีภาพรวมว่าช่างแต่ละคนทำอะไรอยู่ ประโยค template ก็ซ้ำกัน เช่น "มี 0 ใบ ต้องมีอย่างน้อย 10 ใบ" ห้ากล่อง และชื่อเครื่องซ้ำสองบรรทัด
4. **เวลาและตัวเลขขาดบริบท:** มีเวลาที่ไม่มีวันที่ ("07:09", ETA "21:09") ตัวเลขไม่มีหน่วยหรือฐาน (บัฟเฟอร์ "20", ภาระ "14%") ความละเอียดของ ETA ไม่เข้ากับความไม่แน่นอน ±2 ชม. ส่วนผังสายใช้รหัส `st-01`, `line-a` และหน้า loops ใช้ `cycle_time_s`
5. **งานของช่างไม่เหมาะกับถุงมือ:** "ปิดงาน" กับ "ส่งต่อ" เป็นลิงก์ตัวเล็ก ช่องนาทีรอต้องพิมพ์ "0" เอง มองไม่ออกว่าเลือกตัวเลือกไหนแล้ว ปุ่มปิดงานเล็กและชิดซ้าย และอ่านข้อความอังกฤษต้นฉบับของขั้นไม่ได้
6. **ความปลอดภัย:** ขั้นล็อกเอาต์ใช้ปุ่ม "ทำขั้นนี้แล้ว" แตะเดียวเหมือนขั้นอื่น ปิดงานหรือส่งต่อได้โดยไม่ถามสถานะกุญแจ การ์ดบอกจำนวนคันที่จะเสียแต่ไม่บอกว่าต้องหยุดสถานี ส่วนการเน้นขั้นด้วยคีย์เวิร์ดใน v3 พลาดขั้นร้อนกับขั้นหยุดฉุกเฉิน และเน้นขั้นปลดล็อกแบบเดียวกับขั้นล็อก
7. **ใบพิมพ์ใช้แทนใบงานจริงไม่ได้:** ช่องผลมี 3 แบบ แต่ระบบมี 4 ไม่มีนาทีรอ ไม่มี revision หรือผู้อนุมัติ ไม่มีช่องลงชื่อใส่หรือปลดกุญแจ เลข WO ถูกตัด และบนมือถือบอกให้ "กด Ctrl+P"
8. **แจ้งซ่อม:** เลือกเครื่องจาก dropdown ที่มีแต่รหัส ช่อง "เห็นอะไร" บังคับพิมพ์ ปุ่มส่งอยู่ใต้จอ สถานะใช้ภาษาของระบบ และ**แสดงชื่อช่างที่ระบบเสนอก่อนหัวหน้ากะยืนยัน** ซึ่งทำให้ไปตามผิดคนและขัด PDPA
9. **ทางตันและความเชื่อถือ:** หัวหน้ากะเปิดใบงานแล้วเจอหน้าล็อก เครื่องที่มีแจ้งซ่อมค้างขึ้น "ไม่มีสัญญาณผิดปกติ" ข้อความสีเทาอ่อนมี contrast ต่ำกว่าเกณฑ์ หน้า "เชื่อมต่อไม่ได้" ไม่มีข้อมูลล่าสุดและไม่แยกว่า Wi-Fi หลุดหรือ server ไม่ตอบ หน้า sign-in ไม่มีปุ่มแสดงรหัสผ่าน และไม่บอกว่ากำลังเข้า server ไหน

สิ่งที่ผู้ให้ข้อมูลขอให้เก็บไว้: การ์ดงานเดียวที่ชื่อเครื่องตัวใหญ่, หน้า "ไม่มีขั้นตอนที่อนุมัติ อย่าเดา" ที่ชี้หน้าคู่มือ, ประโยค "ระบบนี้เป็นคิวงาน ไม่ใช่ช่องทางฉุกเฉิน", หน้า "เชื่อมต่อไม่ได้" ที่บอกว่างานที่ปิดไว้ไม่หาย

### 0.3 เป้าหมายของ redesign

1. หน้าจอผ่านการตรวจแบบที่โรงงานจริงใช้ และทุกเกณฑ์ตรวจซ้ำได้ด้วยสคริปต์ ภาพ หรือการทดสอบกับคน ไม่ใช่ความเห็น
2. แต่ละบทบาทมีหน้าจอที่เหมาะกับอุปกรณ์ของตัวเอง ได้แก่ ช่างและพนักงานใช้มือถือขณะใส่ถุงมือ หัวหน้ากะใช้แท็บเล็ตกับ desk ส่วนวิศวกรใช้ desk สองจอ
3. ไม่มีหน้าจอใดแสดงสิ่งที่ไม่จริง และไม่สร้างข้อมูลหรือข้อความความปลอดภัยขึ้นเอง
4. ได้หลักฐานสำหรับรายงาน คือ baseline ก่อนแก้, ผลหลังแก้จาก task และ seed ชุดเดียวกัน, ตาราง trace และ design rationale

### 0.4 สิ่งที่เจ้าของโครงการต้องตัดสินใจ (รายละเอียดในส่วนที่ 7)

1. จะเรียกบทสัมภาษณ์ 6 ฉบับในรายงานว่าอะไร `shift-lead.md` เขียนไว้เองว่าเป็น "บทบาทจำลอง" เพราะฉะนั้นต้องไม่เรียกว่าการสัมภาษณ์ผู้ใช้จริง
2. ขั้นความปลอดภัยใน Phase A: ไม่เน้นขั้นใดเลยแล้วเขียนเป็นข้อจำกัด หรือจะเพิ่มฟิลด์ใน backend
3. อนุญาตงาน B ขนาดเล็กที่แค่เปิดฟิลด์ที่ backend เก็บอยู่แล้วใน Phase A หรือไม่
4. นโยบาย session แยกตามบทบาท
5. หน้าวิศวกรและภาพรวมสายใน Phase A จะแก้แค่ระดับทั่วไป (G) หรือออกแบบใหม่ทั้งหน้า
6. แผน baseline และการทดสอบ รวมถึงวิธีใช้ผลของพี่คง

## 3. Requirements

**วิธีอ่านตาราง**
- "ต้อง/ควร" บอกว่าข้อกำหนดนั้นบังคับแค่ไหนในตัวผลิตภัณฑ์ ส่วน MoSCoW (M/S/C/W) บอกลำดับความสำคัญใน redesign รอบนี้ ข้อ "ต้อง" ที่เป็น B อาจได้ S หรือ W เพราะเวลาไม่พอ
- ขอบเขต **F** = ทำได้ในหน้าจออย่างเดียว ด้วยข้อมูลที่ API ให้อยู่แล้ว (`work.ts`, `overview.ts`, `drafts.ts`); **B** = ต้องเพิ่ม backend/API/config และต้องมี ADR; **B-s** = B ขนาดเล็กที่แค่เปิดฟิลด์ที่ backend เก็บอยู่แล้ว
- วิธีตรวจ: **SS** = screenshot อัตโนมัติที่ viewport ระบุ, **SC** = สคริปต์ (DOM/HTTP/print), **UT** = ทดสอบกับคน, **CG** = code grep หรือ lint
- ที่มา: ID เดิมของผู้ให้ข้อมูล (R-T ช่าง, R-S หัวหน้ากะ, R-E วิศวกร, R-H จป., R-P ฝ่ายผลิต, R-I IT, R-A/R-Q กรรมการ), PAT = `patterns.md`, OT = owner-trial

## 4. ความขัดแย้งระหว่างผู้ใช้และการตัดสิน

**4.1 Session 12 ชม. ของช่าง กับ idle timeout 15 นาทีของ IT**
- ทางเลือก: (ก) ทุกบทบาทใช้ timeout 15 นาที (ข) ทุกบทบาทอยู่ได้ 12 ชม. (ค) แยกตามบทบาท
- ผลกระทบ: (ก) ช่างโดนเด้งออกระหว่างรอเครื่องเย็น ข้อมูลที่กรอกเสี่ยงหาย ซึ่ง CMMS ตัวเก่าตายเพราะเรื่องนี้ (ข) PC ห้องหัวหน้ากะที่ใช้ร่วมกันเปิดค้างไว้ในชื่อคนอื่น
- **ข้อเสนอ: (ค)** มือถือช่างเป็นเครื่องประจำตัว จึงให้ session ยาวเท่ากะ + 1 ชม. และใช้การล็อกจอของเครื่องแทน ส่วนหัวหน้ากะและวิศวกรที่ใช้อุปกรณ์ร่วมใช้ idle 15 นาที (REQ-I-05) Phase A ทำฝั่งหน้าจอ ส่วนการบังคับที่ server (REQ-I-11) ต้องตรวจ cookie TTL ปัจจุบันก่อน ถ้าสั้นกว่ากะจะเป็นงาน B ข้อแรกของ Phase B

**4.2 ตรวจจับขั้นล็อกเอาต์จากคีย์เวิร์ด กับเครื่องหมายที่วิศวกรกำหนด**
- ทางเลือก: (ก) ใช้คีย์เวิร์ดบนจอช่าง พร้อมป้าย "ระบบคาดจากข้อความ" (ข) ไม่เน้นขั้นใดบนจอช่าง จนกว่า backend จะมี `Step.kind` (ค) ทำ `Step.kind` + จุดตัด + การยืนยันรายจุดใน Phase A
- ผลกระทบ: (ก) ภาพของทีมเองแสดงว่าคีย์เวิร์ดพลาดขั้นร้อนกับขั้นหยุดฉุกเฉิน และเน้นขั้นปลดล็อกแบบเดียวกับขั้นล็อก จป. ระบุว่า "เน้นบางขั้นแล้วพลาดบางขั้น แย่กว่าไม่เน้นเลย" (ข) ไม่มีการเน้นที่ผิด แต่ขั้น isolation ยังผ่านได้ด้วยแตะเดียว จึงต้องเขียนเป็นข้อจำกัด (ค) ใช้ราว 3 วันทำงาน (schema, หน้าอนุมัติ, snapshot, จอช่าง, เทสต์) ซึ่งเกินงบ Phase A
- **ข้อเสนอ: (ข) ใน Phase A และ (ค) เป็นงานแรกของ Phase B** จอช่างไม่เน้นขั้นจากการเดา (REQ-H-02) ส่วนคีย์เวิร์ดใช้ได้เฉพาะในหน้าตรวจร่างเพื่อช่วยวิศวกร (REQ-E-14) Phase A ยังได้ส่วนที่ไม่ต้องใช้ฟิลด์ใหม่ คือ ไทยคู่อังกฤษทุกขั้น, คำถามสถานะกุญแจตอนปิดงานและส่งต่อ, ตารางลงชื่อกุญแจบนใบพิมพ์ และรายงานต้องเขียนว่า "ยังไม่ใช้กับเครื่องจริง จนกว่าจะมี REQ-H-03 ถึง H-05" เหตุผลคือข้อนี้ตรงกับเงื่อนไขที่ จป. รับได้ และไม่ขัด ADR-003 หรือ ADR-005

**4.3 ความหนาแน่นของข้อมูลหัวหน้ากะ กับความเรียบง่ายของช่าง**
- ทางเลือก: (ก) ใช้ layout เดียวที่ responsive ทุกบทบาท (ข) แยก layout ตามบทบาทและอุปกรณ์ แต่ใช้ token คำสถานะ และรูปทรง priority ชุดเดียวกัน
- ผลกระทบ: (ก) คือสาเหตุของปัญหาเดิม คือหน้ามือถือที่ยืดออก (ข) ต้องเขียน component สองชุด (ตาราง desk กับการ์ดมือถือ) แต่ใช้ข้อมูลชุดเดียว
- **ข้อเสนอ: (ข)** กระดาน desk เป็นตารางแน่นแบบ Excel แถวละ ≤ 2 บรรทัด ส่วนจอช่างเป็นงานเดียวและขั้นเดียว REQ-G-04 ทำให้ทั้งสองจอใช้คำและรูปทรงเดียวกัน จึงไม่ขัด REQ-G-03 หรือ R-S8

**4.4 ค่าเกณฑ์ที่ต่างกัน: contrast 7:1 กับ 4.5:1, ตัวอักษร 18/17/16 px, เป้ากด 56/48 px, viewport 360 กับ 390 px**
- ทางเลือก: ใช้ค่าต่ำสุดที่มีคนเสนอ (WCAG AA) หรือใช้ค่าสูงสุดกับทุกจอ หรือแยกตามความเสี่ยงของบริบท
- ผลกระทบ: ค่าต่ำอ่านไม่ออกในแสงจ้าและกดพลาดเมื่อใส่ถุงมือ ค่าสูงทุกจอทำให้กระดาน desk เห็นงานไม่ถึง 8 แถว
- **ข้อเสนอ:** contrast ใช้ 7:1 กับข้อความเนื้อหา ข้อความตัดสินใจ และข้อความความปลอดภัยทุกจอ ส่วนข้อความรองใช้ 4.5:1 (REQ-G-07) เพราะธีมหมึกบนพื้นขาวทำ 7:1 ได้โดยไม่เสียอะไร ตัวอักษรบนมือถือ ≥ 18 px บน desk ≥ 15 px และไม่มีที่ใดต่ำกว่า 14 px เป้ากดบนจอช่างและแจ้งซ่อม ≥ 56 px ส่วนหัวหน้ากะบนแท็บเล็ตหรือมือถือ ≥ 48 px ทดสอบที่ 360×640 เป็นกรณีแย่ที่สุด และที่ 390×844 เป็นกรณีทั่วไป

**4.5 "ห้ามมีแถบลอยทับเนื้อหา" ของช่าง กับปุ่มหลักแบบ sticky ที่งานวิจัยแนะนำ**
- ทางเลือก: (ก) ใช้ปุ่ม sticky เสมอ (ข) ไม่ใช้ fixed element เลย (ค) ใช้ sticky ได้ก็ต่อเมื่อผ่าน REQ-G-09
- ผลกระทบ: (ก) ข้อความขั้นยาวจะเลื่อนผ่านใต้ปุ่มได้ (ข) ต้องเลื่อนหาปุ่มเมื่อขั้นยาว
- **ข้อเสนอ: (ค)** ไม่ใช้แถบนำทางล่างบนหน้าที่มีเนื้อหาความปลอดภัย ใช้ปุ่มหลักแบบ sticky ได้เฉพาะเมื่อขั้นปัจจุบันทั้งขั้นพอดีเหนือปุ่มที่ 360×640 ไม่เช่นนั้นให้ปุ่มอยู่ท้ายเนื้อหาตามปกติ เกณฑ์ตรวจด้วยสคริปต์ทีละ 100 px ได้ และสอดคล้องกับข้อเท็จจริงข้อ 2

**4.6 จำนวนคันที่เสียบนการ์ด (ฝ่ายผลิต) กับแรงกดดันให้ลัดขั้นตอน (จป.)**
- **ข้อเสนอ:** แสดงจำนวนคันบนกระดานหัวหน้ากะและภาพรวมสาย (REQ-S-03, L-01) แต่ไม่แสดงบนหน้าขั้นตอนของช่าง (REQ-H-12) ส่วนการ์ดของช่างแสดง `reason` ตามที่ backend เขียน (REQ-G-12) เมื่อ REQ-H-03 พร้อม ข้อกำหนดเรื่องการหยุดสถานีหรือล็อกเอาต์ต้องอยู่เหนือปุ่มเริ่ม

**4.7 แจ้งซ่อม ≤ 3 แตะ กับข้อมูลที่ต้องเลือก 3 อย่างบวกปุ่มส่ง**
- การเลือกเครื่อง คำถามเครื่องหยุด อาการ และปุ่มส่ง รวมกันอย่างน้อย 4 แตะ ถ้าเลือกเครื่องเองต้องเลือกสถานีด้วย
- **ข้อเสนอ:** ≤ 3 แตะเมื่อเปิดจาก QR หรือลิงก์เครื่อง และ ≤ 5 แตะเมื่อเลือกเครื่องเอง โดยคงค่ากลางของเวลาไว้ที่ ≤ 20 วินาที (REQ-P-01) เวลาคือสิ่งที่ฝ่ายผลิตต้องการจริง ส่วนจำนวนแตะเป็นตัวแทนของเวลา

**4.8 ทุกขั้นในหน้าเดียวแบบกระดาษ กับทีละขั้นต่อหน้าจอ**
- **ข้อเสนอ:** ใช้ทีละขั้นเป็นหลัก เพราะตัวอักษรใหญ่และปุ่มเดียวเหมาะกับถุงมือและแสงจ้า และมีหน้า "ดูทุกขั้น" แยกกับใบพิมพ์ A4 สำหรับคนที่ต้องการเห็นทั้งหมด (REQ-T-05, T-14)

**4.9 พนักงานอยากรู้ว่าใครจะมา กับ PDPA**
- **ข้อเสนอ:** Phase A ไม่แสดงชื่อช่างกับพนักงานเลย (REQ-P-06) แสดงเฉพาะสถานะ 4 ขั้น ถ้าจะแสดงชื่อเล่นหลังยืนยันต้องให้โรงงานตัดสิน เพราะเป็นเรื่องนโยบาย ไม่ใช่การออกแบบ

**4.10 ยืนยัน 1 คลิกไม่มี dialog (หัวหน้ากะ) กับหน้ายืนยัน (ช่าง)**
- **ข้อเสนอ:** ใส่ friction ตามผลที่ย้อนกลับไม่ได้ การยืนยันของหัวหน้ากะย้อนได้ภายใน 5 วินาที จึงไม่ต้องมี dialog (REQ-S-04) ส่วนการปิดงานและส่งต่อเปลี่ยนสถานะงานและกุญแจ จึงต้องมีหน้ายืนยัน (REQ-T-10) ตามหลักการข้อ 4

### 5.4 Baseline และการใช้ผลทดสอบของพี่คง

- **ต้องวัด baseline ก่อนเปลี่ยน (REQ-A-04)** ถ้าไม่มี baseline รายงานจะอ้างได้แค่ว่า "ดูดีขึ้น" ซึ่งเข้าข่ายเส้นตายกรรมการข้อ 1 ให้แก้ seed ก่อนวัด (A0) เพื่อให้รอบก่อนกับรอบหลังต่างกันแค่ UI ใช้ task และเกณฑ์ "ผลที่ถือว่าแย่" ตามที่เขียนไว้แล้วใน `docs/trial-protocol.md` และ freeze commit ไว้
- **ผลของพี่คงที่กำลังทดสอบ build ปัจจุบันอยู่คือ baseline ที่มีค่าที่สุด** เพราะเป็นผู้ใช้จริงเพียงคนเดียว
  1. ห้าม deploy อะไรทับ build ที่พี่คงใช้ จนกว่าพี่คงจะทดสอบเสร็จ และให้บันทึก commit กับ seed ที่พี่คงใช้
  2. ถ้าทำได้ ขอให้พี่คงทำ task ตาม protocol พร้อมจับเวลาและให้คะแนน SUS ไม่ใช่แค่ส่งความเห็นทาง LINE
  3. ถ้าพี่คงทดสอบด้วย seed เดิม ผลบางข้อจะมาจาก seed (ดู 0.2) ให้คัดข้อนั้นออกโดยระบุเหตุผล ไม่ใช่ลบเงียบ ๆ
- **ข้อจำกัดของหลักฐาน ต้องเขียนในรายงาน:** พี่คงดูแลสายการผลิตของ CPF ซึ่งเป็นอุตสาหกรรมอาหาร ไม่ใช่โรงประกอบรถยนต์ และเป็นวิศวกรหรือผู้จัดการ ไม่ใช่ช่างที่ใส่ถุงมือหน้าเครื่อง ความเห็นของพี่คงจึงมีน้ำหนักมากในเรื่องกระดานหัวหน้ากะ การสั่งงาน ภาษาที่หน้างานใช้ และความน่าเชื่อถือ แต่มีน้ำหนักน้อยในเรื่องถุงมือและหุ่นยนต์ FANUC นอกจากนี้พี่คงเคยเป็นพี่เลี้ยงของนิสิต คะแนน SUS อาจสูงเกินจริง จึงควรเน้นตัววัดที่เป็นพฤติกรรม (สำเร็จหรือไม่, เวลา, จำนวนครั้งที่ถาม) การใส่ชื่อบริษัทในรายงานต้องได้รับอนุญาตก่อน (เส้นตายกรรมการข้อ 6)
- **requirement ใหม่จากพี่คง:** ใส่ลงตารางด้วยแหล่งที่มา "ผู้ใช้จริง" ถ้าได้รับก่อน 18 พ.ย. ให้พิจารณาเข้า Phase A ถ้าได้รับหลังจากนั้นให้เข้า Phase B ห้ามแก้เกณฑ์ผ่านของรอบหลังหลังจากเห็นผลแล้ว (เส้นตายกรรมการข้อ 4)
- **รอบหลัง:** ใช้ผู้ทดสอบ ≥ 5 คน (พี่คง + ตัวแทนที่ระบุว่าเป็นตัวแทน) ถ้าใช้พี่คงซ้ำต้องอธิบาย learning effect
